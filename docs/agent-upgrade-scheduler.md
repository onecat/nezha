# Dashboard scheduler admission and transfer claim

The scheduler is disabled by default. It requires an independently provisioned trusted Eligibility implementation for the authenticated operator, server ownership, live authenticated Agent capability and durable release sequence. It accepts only Linux amd64 or arm64, and each architecture requires explicit local qualification; Windows packages remain valid format objects but cannot be admitted or dispatched. No architecture is enabled by default.

Admission reopens and verifies the signed package, creates a random task ID with a fixed 15-minute expiry, and atomically writes the task and immutable operator admission audit. SQLite admission caps all nonterminal tasks at three across restarts; a busy/error is not a successful reservation. The existing low-level Store.Create is retained for tests and migration but cannot create a dispatchable audited task. A transfer claim reloads the durable admission, verifies authenticated server identity, rechecks current eligibility and signature, then CAS-claims the task and returns an owned read-only bounded chunk source. No task is marked installed or successful by transfer.

No HTTP/gRPC handler, actual session authentication provider, capability negotiation, receipt handling, durable server high-water provider, full transition audit or batch/canary queue is wired. The future caller must close transfer descriptors, handle deadlines and reconcile failed or expired reservations without guessing Agent installation status. No production startup integration or UI enablement. Tests use real SQLite, signed synthetic packages and simulated eligibility, not a live Dashboard/Agent network connection.
