# Explicit Dashboard managed upgrade provisioning

No setting is enabled by default. NZ_MANAGED_UPGRADE_CONFIG points to an absolute private JSON file (0600, trusted local directory). Fields: enabled, allow_execution, package_dir, linux_amd64, linux_arm64, keys (key ID to hex Ed25519 public key), targets (id, secret_sha256, arch, initial_sequence). The target list is a local operator attestation of migrated, supervisor-capable Linux Agents; no version string alone grants capability. The secret fingerprint prevents a changed or reused server identity from silently retaining authorization. Both platform switches are off by default. Only the configured local superadmin with a live session can admit work, and the check is repeated before dispatch/grant. Dashboard tracks the highest previously granted sequence; local Agent state remains authoritative.

When valid enabled provisioning is loaded, the legacy and new gRPC service listen on 127.0.0.1 rather than all interfaces: a same-host TLS-terminating Nginx proxy is required, with protected local backend. This is an explicit deployment constraint and not compatible with a remote/container-network proxy without additional work. Invalid config disables upgrades and preserves legacy listener behavior. Do not enable in production before complete qualification.

The server-list toolbar now places 升级 Agent immediately before batch group edit; it is disabled unless the explicit execution switch and HTTPS local administrator session are present. Existing same-origin mutation middleware protects raw package upload and JSON wave admission. Uploads have a two-minute read deadline and 100 MiB cap; the private repository conservatively reserves disk space under a 2 GiB/128-entry quota. The user chooses one canary then explicitly requests waves of up to three targets using the successful same-package canary task ID; partial admissions are returned. This is manual staged rollout, not autonomous fleet scheduling. Status is available by task ID; the interface is a minimal toolbar interaction, not a full task history dashboard. Expired pre-grant tasks are released on admission; unresolved granted tasks are never guessed terminal. No production activation performed. Agent supervisor startup and live cross-repository testing remain required.
