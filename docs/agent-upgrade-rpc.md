# Managed upgrade v1 transport (development)

Separate gRPC service nezha.upgrade.v1.ManagedUpgrade uses standard protobuf BytesValue messages with a bounded binary header and chunks. Legacy NezhaService descriptors are unchanged. Download authenticates the server identity, requires direct TLS or an explicitly trusted local loopback proxy, enforces a client deadline of at most two minutes, and claims a pending audited task by CAS. Header binds task identity, version, sequence, expiry and size; each chunk is ordered by offset within that stream. Successful EOF follows a durable delivery marker. Verify accepts only the exact authenticated task identity and an existing delivery marker. Duplicate exact verification receipts are idempotent while valid. An acknowledged verified state does not authorize installation.

The service is registered disabled in the normal Dashboard listener. No production scheduler/eligibility provider is configured yet. Interrupted transfers remain reserved for explicit reconciliation. No remote install command or final success receipt is accepted at this stage. The client must use certificate-validated TLS and a private staged file, verify the signature and sequence, and must not install just because Verify succeeded.
